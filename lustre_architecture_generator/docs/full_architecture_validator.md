# H10 — Full deterministic architecture validator

H10 is the independent hard validator for complete architectures generated by
H8. It is intentionally independent of the H9 soft score.

## What H10 recomputes

For each architecture, H10 starts from the selected drive IDs, protection
profile IDs and hardware component IDs and recomputes:

1. H5 MDT protection arithmetic;
2. H5 OST protection arithmetic;
3. H6 MDT hardware-path compatibility and minimum resources;
4. H6 OST hardware-path compatibility and minimum resources;
5. H7 aggregate counts, performance, cost and power.

It then checks the hard case constraints:

- MDT capacity / read IOPS / write IOPS;
- OST usable capacity / read bandwidth / write bandwidth / total bandwidth;
- RAID/protection geometry and physical drive counts;
- drive/controller/server/enclosure/network/HA compatibility;
- controller/enclosure/network resource minimums;
- total budget;
- total power;
- HA requirement.

The validator does not trust the stored H5/H6/H7 values: it recomputes them and
compares the results.

## Decision

Each complete state receives one H10 decision:

- `VALIDATED` + `is_valid=true` if no hard violation exists;
- `INVALID` + explicit violation codes otherwise.

The H7 terminal state semantics are extended backward-compatibly so
`PENDING_FULL_VALIDATOR`, `VALIDATED` and `INVALID` are all valid terminal
statuses with strict consistency rules.

## No scoring and no Beam Search

H10 does not import or require H9 scoring to make its decision. A high H9 score
cannot rescue an invalid architecture.

Beam Search is not used.

## Important interpretation of runtime coverage

The current runtime validation deliberately uses the same controlled H8 limits
used in previous gates (for example 16 architectures per case). Therefore:

- a case with zero valid architecture under this capped pool is not a validator
  runtime failure;
- it may mean the case is truly infeasible under the reference catalog, or only
  that the capped H8 prefix did not yet include a feasible architecture.

Before the Architecture Layer is frozen, a separate feasibility-coverage pass
must distinguish these two situations by expanding the deterministic H8 search
for cases without a valid architecture.
